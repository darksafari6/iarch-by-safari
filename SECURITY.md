# Security policy

## Reporting a problem

Report anything that could be exploited — a command that runs with privileges it
does not need, a path that lets an installer overwrite a file it should refuse, a
package fetched without verification — through GitHub's **private vulnerability
reporting** on this repository (`Security` → `Report a vulnerability`). If that
button is not available, open a normal issue and say only enough to be contacted;
do not post a working exploit in public.

There is no `security@` address and no bug bounty. The maintainer listed in
[`README.md`](README.md) reads every report. Expect an acknowledgement rather
than a fix deadline: this is one person's desktop configuration, published as
free software, with no support contract behind it.

Everything else — a package that is missing on your distribution, a keybind that
does nothing on your hardware, a document that contradicts the code — belongs in
a regular issue, or in [`docs/UNVERIFIED.md`](docs/UNVERIFIED.md) if it is a
claim nobody has proven yet.

## What the installers do with root

`install.sh` and `fedora_install.sh` are meant to be run with `sudo` on a fresh
machine you are prepared to reinstall. They are not sandboxed and they change
system state. As of this revision the privileged operations are:

| Operation | Where | Why it matters |
| :--- | :--- | :--- |
| `pacman -S --noconfirm`, `pacman -Syu --noconfirm` | `install.sh` | Installs and upgrades without a per-package prompt (`INS-01`) |
| `yay -S --noconfirm` for the AUR greeter package | `install.sh` | Builds third-party code from the AUR without review (`INS-02`) |
| Edits `/etc/pacman.conf`: uncomments `[multilib]`, appends and reorders `[chaotic-aur]` | `install.sh`, `ensure_multilib_repo_enabled` and `reorder_pacman_conf` | Backs the file up to `/etc/pacman.conf.bak.<epoch>` first |
| `pacman-key --recv-key 3056513887B78AEB` from `keyserver.ubuntu.com`, then `pacman -U --noconfirm` of `chaotic-keyring` and `chaotic-mirrorlist` from `cdn-mirror.chaotic.cx` | `install.sh`, `install_chaotic_aur` | Trusts a third-party packager and fetches packages over the network (`TP-05`) |
| `dnf -y copr enable` for three COPRs | `fedora_install.sh:92-104` | Adds third-party build repositories system-wide |
| `sudo systemctl disable sddm` then `sudo systemctl enable greetd` | `install.sh:1530-1533` | Replaces the display manager; this is the change most likely to leave a machine unbootable into a graphical session (`INS-03`) |
| `systemctl enable --now cups`, `systemctl enable bluetooth`, `accounts-daemon` | `install.sh:778`, `install.sh:798`, `fedora_install.sh:510-529` | Changes which services start at boot |
| `chown -R` on `/var/lib/noctalia-greeter` | `fedora_install.sh:554` | Ownership change, scoped to one directory the installer created |
| `rm -rf` on the staging directory it created | both installers | Scoped to a temporary directory the script owns |
| Offers `ttf-ms-fonts` and other AUR packages whose redistribution terms were not verified | `install.sh` printer-support step | See `TP-12` in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md) |

The ids in that table are rows in [`docs/UNVERIFIED.md`](docs/UNVERIFIED.md). They
are known, documented deviations from the safety contract, scheduled for the
installer hardening pass — not accepted behaviour.

## What they deliberately do not do

- **No `curl | bash`.** Every script runs from a checkout you can read first.
- **No silent package removal.** Removals are listed, explained and need an
  explicit answer; additions are recorded by `lib/package-audit.sh` so a later
  run can tell you what it added.
- **No blanket `chown -R` of a config tree.** Ownership changes are limited to
  paths the installer created.
- **Backups before overwriting.** `lib/iarch-common.sh` writes a timestamped
  `.bak.<timestamp>` copy and `uninstall.sh` restores from those; generated files
  additionally keep the last five generations under
  `~/.local/state/iarch/backups/`.
- **Refusal of ambiguous targets.** Symlinks, files whose content differs from the
  shipped source, and paths this repository does not manage are reported and left
  alone (`lib/managed-files.sh`).
- **No telemetry and no runtime fetching from this repository.** Nothing under
  `.config/`, `scripts/` or `lib/` calls `curl` or `wget`. The only URLs in the
  session payload are the two `$schema` hints at the top of
  `.config/fastfetch/config.jsonc` and `.config/starship.toml`, which editors
  read and the programs themselves ignore. Network access during installation is
  the package manager, the keyring fetch and the greeter package. The shell and
  compositor are upstream software with their own behaviour, credited in
  [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).

## The lock screen

`.config/hypr/hyprlock.conf` is generated by `python3 iarch/cli/render_hyprlock.py`
from the design tokens, and it is worth being precise about what a lock screen
does and does not protect.

- **Authentication is PAM's, not this repository's.** The file sets
  `pam:enabled = true` and leaves `pam:module` at hyprlock's own default, so
  hyprlock asks PAM and falls back to the `su` module when `/etc/pam.d/hyprlock`
  does not exist. No password is read, stored, hashed or transmitted by anything
  in this repository, and there is no key in hyprlock that would let one be.
- **`SIGUSR1` unlocks hyprlock without a password.** That is hyprlock's
  documented behaviour: `pkill -USR1 hyprlock` from another TTY ends the lock. It
  is not a misconfiguration and this repository cannot turn it off, which is the
  reason for the sentence below.
- **A lock screen is not a boundary against a local user who can already run
  commands as you.** Anything that can signal your processes can unlock one, read
  your files and change this configuration. The lock screen keeps a session
  private from somebody walking up to it, and that is the whole claim.
- **Nothing on the lock surface runs a command.** hyprlock can attach `onclick`
  to a label, image or shape and can run a shell command on a timer inside a
  label (`cmd[update:1000] …`); the generator emits neither, and
  `tests/test_hyprlock.py` fails if one appears. A lock screen that can run a
  command on click is a lock screen with an unlock bypass one misclick away.
- **Account lockout is the distribution's.** On Arch, pambase wires
  `pam_faillock.so` into hyprlock's PAM module, which locks the account for ten
  minutes after three failed unlocks. Changing that means editing
  `/etc/security/faillock.conf`, a system file this repository does not write.
- **Only one lock client can hold the session.** Noctalia's own lock screen and
  hyprlock both implement `ext_session_lock_v1`, and the protocol gives it to
  whichever asks first. `Super + L` and the shell's session menu therefore lock
  through the shell while it is running, and hyprlock is the lock screen for a
  session where it is not — which is what `lock_cmd = pidof noctalia || hyprlock`
  in the shipped `hypridle.conf` expresses.

## The login screen

`greetd` runs `noctalia-greeter-session` as the unprivileged `greeter` account,
and the greeter collects the password through greetd's PAM conversation. This
repository writes two things that touch it and refuses to write a third.

- **The installers write `/etc/greetd/config.toml`.** Two tables, three keys:
  `[terminal] vt = 1`, and `[default_session] command` and `user`. They back up
  an existing file first, and they are the same three keys upstream's own helper
  prints (`scripts/greetd_setup_lib.sh:107-112` in noctalia-greeter v1.7.0).
- **They create `/var/lib/noctalia-greeter` at mode 0750, owned by `greeter`.**
  It holds `sync.toml`, any `greeter.toml`, and the synced wallpaper images. No
  secret lives there — no password, no hash, no key material — but the greeter's
  own setup treats the directory as private to its account
  (`kSyncedDirMode`, `src/greeter/greeter_preferences.cpp:29`), and both
  installers now do the same. They previously left it at the umask default of
  0755, which let any local user list a machine's wallpaper and monitor layout.
- **They delegate PAM to the packaged script, and never write `/etc/pam.d`.**
  `/usr/share/noctalia-greeter/setup_greetd_pam.sh` inserts
  `session required pam_systemd.so` (or `pam_elogind.so`) into
  `/etc/pam.d/greetd` when it is missing, backing the file up first, and exits
  without touching anything when greetd is not installed or no runtime module
  exists. Without that line a session started at the login screen is not
  registered with logind, and the lock screen and idle behaviors that follow
  depend on logind knowing the session exists. A missing script is a warning,
  not a failed install.
- **No `greeter.toml` ships.** The greeter's declarative config is root-owned,
  wins over Sync for every key it sets, and only ever warns about a value it does
  not like — so a file this repository guessed at would be a login screen that
  quietly looks default, on a machine that cannot tell the difference. Its
  `[auth] allow_empty_password` defaults to `false` and stays that way, which is
  the same posture the lock screen takes: an empty submission is not a
  convenience worth accepting.
- **No passwordless privilege rule is installed.** Syncing appearance to the
  login screen elevates through `pkexec`, and the packaged action
  `org.noctalia.greeter.sync-appearance` requires administrator authentication in
  all three polkit states. Passwordless sync is a per-account opt-in
  (`sudo noctalia-greeter passwordless-sync enable <user>`) that writes a narrow
  rule for one helper, one target account and one user in an active local
  session. This repository does not run it, does not write a rule of its own, and
  leaves `[shell.greeter_sync] auto_sync` off — with auto-sync on and no rule
  installed, every wallpaper change would raise an authentication dialog.
  `[shell.greeter_sync] privilege_command` is a prefix the shell appends `--sync`
  to and runs as root, so the renderer refuses it rather than emitting one.
- **One polkit agent, started by the session.** `.config/hypr/startup.lua:19`
  starts `polkit-gnome-authentication-agent-1` (`xfce-polkit` on Fedora), which
  is what the Sync prompt appears in. The shell's own agent stays off, because
  two agents on one seat compete for the same request.

`data/design/greeter.json` records the whole login-screen surface — both files,
the precedence between them, what Sync carries and what it cannot, and four
places where the greeter's documentation disagrees with its code.

## Scope

Only the current session payload is in scope: `.config/`, `lib/`, `tools/`,
`iarch/`, `scripts/` and the two root installers. `legacy/` is a frozen
configuration for an older session, kept so existing installs can still roll
back; it is maintained for correctness but not hardened further, and running
`legacy/install-v4-session.sh` today is discouraged.

Runtime helper scripts under `scripts/` are read-only or allowlisted:
`iarch-healthcheck.sh` changes nothing, and `iarch-control-center.sh` only sends
shell IPC commands from a fixed list.

The two mode switches send IPC and nothing else. `iarch-gamemode` runs
`iarch-theme` and `iarch-anim` in-process and then asks the compositor and the
shell to reload; `iarch-focus` asks the shell for Do Not Disturb and caffeine and
sends the compositor one `hyprctl eval` carrying two decoration values. That eval
is worth stating plainly, because it is the sharpest thing in this repository:
`hyprctl eval` runs Lua inside the compositor, so anything that can write to
`$XDG_RUNTIME_DIR/$HYPRLAND_INSTANCE_SIGNATURE/.socket.sock` can already change
any config leaf, and this project adds no capability the socket does not have.
What it does add is discipline — the values come from `data/design/tokens.json`
(`modes.focus`), never from an argument, so the command cannot be pointed at an
arbitrary leaf; `hyprctl keyword`, the spelling a reader of the shipped manual
would reach for, is not used because v0.57.2 does not register it and would answer
`unknown request` while still exiting 0. Neither switch runs a shell, and neither
writes a file that is not generated.

## If something already went wrong

1. Do not run the installer again.
2. `bash scripts/iarch-healthcheck.sh` reports what it can see without changing anything.
3. `./uninstall.sh` restores the timestamped backups it finds and tells you which
   files it restored and which it left alone.
4. System-level changes the uninstaller does not touch — enabled services, added
   repositories, installed packages — are listed in the installer output and in
   [`InstallNotes.md`](InstallNotes.md). Reverting those is manual, by design:
   this repository will not remove packages on your behalf.
